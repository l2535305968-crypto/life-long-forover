> 本文是唯一权威的执行路线图。每条工作流都写明：**用什么角色（以谁的身份做）**、**用什么技能（怎么做）**、**产出什么文件**、**怎么验收才算完成**。
> 依据 `D:\AI\skills\MEMORY.md` 第 0 节选型协议，编码类任务每阶段至少挂 1 个工程角色 + 1 个把关角色，不裸写。

---

## 0. 一句话目标

让 AI 以**晚辈**的身份陪老人聊天，把普通人的一生整理成一本人味儿的"人生之书"：能追问、能听方言、能整理成时间线和传记、能由老人授权家人查看。老人全程只做一件事：**说话**。

---

## 1. 已锁定的关键决策（不再反复）

| 决策 | 结论 | 原因 |
|------|------|------|
| 形态 | 家人发起的 PWA（手机"添加到主屏幕"= 一个大图标） | 老人不会找文件、输网址、装东西 |
| 联网 | 必须联网 | "AI 会聊天"和"听方言"都在模型里，离线就退化成查户口 |
| 对话模型 | DeepSeek（deepseek-chat） | 用户有 Key，已选 |
| 语音转文字 | 先"录音留原声 + 家人用手机输入法听写"，方言 ASR 留接口 | DeepSeek 无 ASR；不假装没验证的能力能用 |
| 部署 | 本机 `node server.mjs` 开发验证；真机用 cloudflared https 隧道；正式托管 Cloudflare Pages/Workers 或 Vercel | 手机要麦克风 + PWA 必须是 https |
| 隐私 | Key 只在服务端；老人内容只存自己手机；服务端不落盘、不打印正文 | 高度隐私，底线 |

---

## 2. 技术栈

**零 npm 依赖。** 服务端用 Node 内置 `http`，前端原生 ESM + IndexedDB + Web Speech / MediaRecorder。好处：不锁 npm 生态、云上托管也简单、部署面小。

## 7. 风险与已知限制（不藏着）

- 语音听写依赖手机输入法/系统能力，方言识别在拿到专业 ASR Key 前只能"听懂多少算多少 + 家人纠错"。
- 局域网 http 地址拿不到麦克风，真机必须走 https 隧道或托管。
- 传记正文只写老人真说过的话，素材不够时会"短且实"，不会编来凑字数——这是特性，不是缺陷。
